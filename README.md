# Fuentes Archive

An iOS app that watches **Nicholas J. Fuentes’ Rumble Videos tab** and saves new public uploads into the Files app. It is meant to be sideloaded with [SideStore](https://sidestore.io) using a free Apple ID. The IPA is unsigned on purpose. SideStore re-signs it.

| Shorts (not downloaded) | https://rumble.com/c/nickjfuentes/shorts |
| Live (not downloaded) | https://rumble.com/c/nickjfuentes/livestreams |

## What it does

- On launch, on pull-to-refresh, and from a background refresh, it reads the Videos tab and remembers every video it sees.
- The first successful sync is a **baseline**. Videos already on the channel are listed and are not downloaded. Anything that shows up later on page 1 is queued automatically when auto-download is on. This is so the first launch does not try to save a thousand multi-gigabyte files.
- You can download any listed video yourself, or tap **Download newest 5 / 10**. Settings has “on first sync, also download newest N”.
- Files are written to the app’s Documents folder (`On My iPhone → Fuentes Archive → Videos`) because `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` are set. They show up in the Files app.
- Optional: also copy a finished file into Photos. Off by default.
- Search, sort, filters, per-video delete, hide, storage totals, and a refresh log.
- A **local** RSS file of the Videos tab can be written into Documents and shared. That file is generated by the app. It is not a Rumble feed.

Wi-Fi only is on by default. A recent 67-minute video is about 2.0 GB at 1080p and about 1.0 GB at 720p. Default quality is **up to 720p**.

## How the listing is scraped

Rumble has no public API for a channel’s Videos tab. These were checked on 11 November 2026:

| URL | Result |
| --- | --- |
| `https://rumble.com/feeds/c/nickjfuentes` | **410 Gone** |
| `https://rumble.com/feeds/user/nickjfuentes` | **410 Gone** |
| `https://rumble.com/feeds/channel/nickjfuentes` | **410 Gone** |
| `https://rumble.com/api/Media/list?channel=nickjfuentes&type=videos` | JSON error: you must be signed in |
| `https://rumble.com/api/Media/search?channel=nickjfuentes` | Same sign-in wall |
| `https://rumble.com/api/Media/oembed.json?url=…` | Works, but for **one video**, not the channel |
| `/api/v1/…`, `/api/Listing/…`, `/-htmx/…` | 404 or an HTML error page |

There is no undocumented feed or lightweight JSON list that returns this Videos tab without the HTML page. The app scrapes that page.

The server HTML contains:

```html
<rum-videos-grid>
  <script type="application/json">{ "items": [ … ] }</script>
</rum-videos-grid>
```

Each item has `object_type`, `id`, `permalink_id`, `title`, `url`, `thumb`, `upload_date`, `duration`, `views`, `is_short`, `live`, `live_placeholder`, `livestream_status`, `visibility`, and `by`. After Rumble’s page script runs, that JSON node is removed and the same cards are `<rum-video-thumbnail video-title="…" video-id="…" url="…">` tags. The parser accepts both. It prefers the JSON, because that is what `URLSession` receives (it does not run the page’s JavaScript) and because the JSON carries members-only and premiere flags.

Items are dropped or held back:

- `is_short`, kind `short`, or a `/shorts` URL — not saved
- `live` or livestream status `live` — not saved
- `object_type` other than `video` — not saved
- `visibility` other than `public`, or availability `premium` / `subscribers` / `members` / `private` — shown as members-only, not downloaded
- `live_placeholder` or status `upcoming` / `scheduled` / `premiere` — shown as a premiere and retried on a later sync
- `is_processing` — waited on, not failed forever

Duplicate cards in the HTML are merged by video id. Tracking query `e9s` is stripped. Pagination uses `<link rel="next">`, then the smallest `?page=` number greater than the current page. The app stops when a page is entirely videos it already knows, or after the page limit (default 2, max 10).

## How the file URL is resolved

The listing’s `eid` field is **not** an embed id. Using it as one returns a different video. The numeric `id` and the `v…` permalink are the stable ids.

For each download:

1. `GET https://rumble.com/api/Media/oembed.json?url=<watch page>`
2. Read the embed id from the iframe, for example `https://rumble.com/embed/v7fz69o/` for “Nick Fuentes on the Alex Jones Show”.
3. Try `https://rumble.com/embedJS/u3/?request=video&ver=2&v=<embed id>`.
4. If that response is not JSON (Cloudflare often challenges it), open `https://rumble.com/embed/<embed id>` and parse the player object assigned to `p.f["<embed id>"]`. The assignment ends with `,loaded:v()`, which is JavaScript and is stripped before JSON parsing.

The player `ua` map has several kinds of URL:

- **mp4 / webm** — one progressive file. Preferred when it exists (older uploads).
- **tar** — a per-quality HLS media playlist stored as a byte range inside a `.tar`. Current Videos-tab uploads use this. The media segments are MPEG-TS (`video/mp2t`) and the ones checked here contain both H.264 and AAC, so concatenating them keeps the audio.
- **hls / auto** — a master playlist of those same tar playlists. Used if a sized rendition is missing.
- **timeline** — a tiny MP4 scrub preview (about 11 kbps). It is an MP4 and it is **not** the movie. The resolver never selects it.
- **audio** — a standalone AAC file. Not selected as the video.

“Best” picks the highest real rendition. A cap such as 720p picks the highest rendition at or below that height. The Alex Jones video exposes 240/360, 480, 720, and 1080. Best selects the 1080p tar, not the timeline MP4.

Downloads use a background `URLSession`, so a transfer keeps going after you leave the app. Progressive files keep resume data. HLS downloads keep a manifest and the pieces already written, and continue at the first missing piece. A failed piece is retried up to five times (30s, 2m, 10m, 30m, 2h). HTTP 404, 410, and 451 are not retried. Other people’s videos and members-only items are not retried forever.

If the phone does not have room for the estimated size plus 64 MB, the download fails with a clear error instead of filling the disk.

## Background refresh, honestly

Two different mechanisms are easy to mix up:

1. **A download that has already started** uses a background URL session (`com.local.fuentesarchive.downloads`). iOS is reasonably good at finishing that transfer after the app is suspended. It still pauses on Low Power Mode, when the system is under pressure, and when Wi-Fi only is on and you are on cellular.
2. **Noticing a new upload** uses `BGTaskScheduler`: a `BGAppRefreshTask` (`com.local.fuentesarchive.refresh`, earliest 15 minutes) and a `BGProcessingTask` (`com.local.fuentesarchive.processing`, earliest 30 minutes, requires network, does not require power). iOS does **not** promise these will run on a schedule. They often wait hours. They may not run at all if the app is force-quit, if Background App Refresh is off, or if you rarely open the app. The practical way to catch a new video quickly is to open the app or pull to refresh.

There is no push entitlement. A free SideStore Apple ID cannot use push, and this app does not ask for it. The optional notification is a **local** notification fired when a download finishes while the app is running or woken for the background session.

You can see what the app attempted in **Settings → Background refresh log**.

To simulate a refresh in the debugger:

```
e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"com.local.fuentesarchive.refresh"]
```

## SideStore

Entitlements are empty. Background modes are Info.plist only (`fetch`, `processing`). There is no App Group, iCloud, associated domains, or push. Photos access is add-only and only if you turn the setting on.

A free Apple ID signature lasts about **7 days**. SideStore has to refresh the app before that or it will not open. That limit is Apple’s, not this app’s. SideStore also needs its pairing / anisette setup already working; this repo does not install SideStore itself.

### Install the IPA you already have

1. Build the IPA (below) or download the `FuentesArchive-unsigned-ipa` artifact from GitHub Actions.
2. Get `FuentesArchive-unsigned.ipa` onto the phone (AirDrop, iCloud Drive, or a direct download in Safari).
3. Open SideStore → the **+** or **My Apps** import → choose the IPA. You can also share the file from Files into SideStore.
4. Sign in with the Apple ID SideStore is using when it asks. It should be the free account already trusted on the phone.
5. Wait for the install. If iOS says the developer is untrusted: **Settings → General → VPN & Device Management** and trust the certificate.
6. Open **Fuentes Archive**. The first sync lists the Videos tab and does not download the back catalog. Pull to refresh, or tap **Download newest 5**.

### Add it as a SideStore source (for updates)

`sidestore/apps.json` is an AltStore/SideStore source. `downloadURL` and `iconURL` are placeholders (`https://REPLACE_WITH_YOUR_HOST/...`). SideStore can only refresh from a real HTTPS URL.

1. Host `FuentesArchive-unsigned.ipa` and `sidestore/icon-1024.png` somewhere HTTPS.
2. Edit `sidestore/apps.json`: set `downloadURL`, `iconURL`, and `size` (bytes of the IPA).
3. Host `apps.json` at a stable URL.
4. In SideStore: **Sources → +** and paste that URL.
5. Later versions: bump `version` / `buildVersion`, point `downloadURL` at the new IPA, and SideStore’s refresh will offer the update. The bundle id must stay `com.local.fuentesarchive`.

You do not need the source to install the first copy. The source is only for updates.

## Build the unsigned IPA

Requirements: macOS with Xcode 16 or newer. No paid developer account.

```bash
bash scripts/build-unsigned-ipa.sh
```

The IPA is written to `build/FuentesArchive-unsigned.ipa`. It is a zip of `Payload/FuentesArchive.app` with no signature. Do not open it in App Store Connect.

Unit tests on a simulator:

```bash
xcodebuild test \
  -project FuentesArchive.xcodeproj \
  -scheme FuentesArchive \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  CODE_SIGNING_ALLOWED=NO
```

This repository’s GitHub Actions workflow (`.github/workflows/ipa.yml`) runs the parser fixtures, a live Rumble check, the XCTest bundle, and uploads the unsigned IPA as the artifact `FuentesArchive-unsigned-ipa`.

The machine that prepared this project is Linux and does not have `xcodebuild`, so the IPA was **not** built here. The Xcode project, the build script, and the workflow are what produce it.

Parser checks that do run here:

```bash
python3 scripts/verify_rumble.py          # saved responses
python3 scripts/verify_rumble.py --live   # the live Videos tab, oEmbed, embed qualities, and the removed feeds
```

`scripts/rumble_parse.py` is the same listing and stream logic the Swift parser is tested against. Fixtures live in `FuentesArchiveTests/Fixtures/`.

## Known limits

- **No IPA was produced in this environment.** There is no Xcode here. CI is set up to build it.
- **Cloudflare** sits in front of channel HTML from a lot of datacenter addresses. Direct fetches of the Videos tab from this network returned 403. A reader proxy could render page 1 (that is how the live titles were confirmed) but not page 2. The app uses `URLSession` with a Safari user agent, which is a normal iPhone client and usually gets the HTML. If a network still shows the challenge, the library is left alone and the error is shown. An empty parse is not treated as “the channel deleted everything”.
- **Page 2 of the live site** could not be rendered from here. Pagination is still covered: the live page-1 HTML has `rel=next` and links through page 48, and a same-crawl archive of page 2 (3 November 2026, 25 different videos, next page 3) is a fixture. The first title on that page is “I'M SICK OF THESE FREAKS!!!”, which is not on page 1 of that crawl.
- **Current uploads are not progressive MP4s.** They are MPEG-TS pieces inside a tar-backed HLS playlist. The app concatenates those pieces into a `.ts` file. The in-app player uses `AVPlayer`. Photos often refuses `.ts`; the file remains in Files, and VLC will open it. Older uploads that still publish a real MP4 are saved as `.mp4` and can be copied to Photos.
- **The timeline MP4 is a trap.** It looks like a video file and it is not the episode. Tests lock that it is never chosen.
- **Background discovery is best-effort.** See above. Do not expect a new upload to appear within minutes if you never open the app.
- **Wi-Fi only and disk space.** A single episode can be 1–4 GB. The default will wait for an unmetered, unconstrained network.
- **Members-only and premieres** are not downloaded. If a premiere later becomes a public VOD, a later sync can queue it.
- **The whole back catalog is not downloaded automatically.** That is deliberate. Use Download newest, or raise the first-sync backfill, if you want older videos.
- **Seven-day SideStore expiry** still applies.
- **Rumble can change the HTML.** The parser accepts the JSON grid and the thumbnail tags. If both disappear, sync fails visibly instead of saving the wrong tab.
